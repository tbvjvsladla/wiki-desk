# 선택형 운영 권고 — 문서 역할 · 헌장 연계 · 검증 효율

이 문서는 wiki-desk를 쓰는 프로젝트에 **제안**하는 운영 방식이다. 스킬 설치·입고·질의에는 하나도 필요하지 않다. 셋 다 채택하지 않아도 wiki-desk는 정상 동작한다.

## 적용 경계 (먼저 읽는다)
- **설치 요청은 권고 적용 요청이 아니다.** "스킬을 설치해 줘"에 헌장 개정·폴더 신설이 포함됐다고 추론하지 않는다.
- **무응답·거절은 승인이 아니다.** 권고 하나를 채택했다고 나머지까지 적용할 권한이 생기지 않는다(예: 네 역할 폴더만 채택 ≠ 헌장 개정 승인).
- **사용자가 적용을 요청하면 제안이 먼저다.** ① 기존 구조(문서 폴더·명명·규칙 파일) ② 권고와의 차이 ③ 영향 ④ 만들거나 고칠 파일 목록을 먼저 보여 주고, 승인된 범위만 수행한다. 적용 뒤 `git diff`로 바뀐 파일이 승인 범위와 같은지 확인한다.
- 기존 프로젝트의 동등한 문서 종류·폴더·명명·언어·메타데이터를 존중한다. 이름을 맞추려고 문서를 옮기거나 다시 쓰지 않는다.
- wiki-desk 명령은 원문을 고치지 않는다. 권고를 적용하더라도 원문 수정은 사람이나 에이전트의 별도 편집이며, 위키 명령이 하지 않는다.

## REC-01 — 최소 네 문서 역할 (선택)
새 프로젝트라면 네 종류의 문서를 담는 네 역할 폴더를 **선택적으로** 둘 수 있다. 네 파일을 무조건 만들라는 뜻이 아니다. 실제 작업의 의도·계획·실행·검증 시점에 맞춰 쓴다.

| 폴더 예시 | 역할 | 담을 내용 |
|---|---|---|
| `docs/interview/` | 의도·합의 | 목표, 범위, 제약, 사용자 결정, 미결정 |
| `docs/plan/` | 계획 | 변경 범위, 순서, 완료 기준, 필요한 검사, 재개 지점 |
| `docs/devlog/` | 실행 기록 | 실제 변경, 시도·실패, 결정, 현재 상태 |
| `docs/checklist/` | 검증·종료 | 기대 조건, 관측 결과, 실행 상태, 근거, 잔여 사항 |

- 장점: "왜 이렇게 정했나(interview)"와 "실제로 무엇을 했나(devlog)"가 분리돼, 질의 때 결정 문서와 결과 문서를 따로 찾을 수 있다. 계약의 `authority_rules`에 역할별 순위를 줄 수 있다.
- 공통 작업 식별자(예: 파일명의 날짜·시각 줄기)와 원문으로 돌아가는 참조(저장소 상대 전체 경로)를 두면 `related` 칸이 문서를 이어 준다.
- 계획을 실행 사실로 적지 않는다. 파일이 존재한다고 사용자 승인으로 취급하지 않는다.
- **기존 구조가 있으면**: 역할 대응만 설명하고 문서는 그대로 둔다. 동등 역할이 없는 기존 문서도 합의한 계약 범위 안이면 그대로 입고·조회된다. 폴더 이름·한국어 파일명·시간대·문서 수는 스킬 사용 조건이 아니다.
- **미채택**: 아무것도 하지 않는다.

## REC-02 — 두 종류의 규칙과 호스트 진입점 (선택)
작업 수행과 문서 발행의 책임을 나눠 안내하는 방식을 **선택적으로** 쓸 수 있다.
- **작업수행규칙**: 목표·권한 범위, 계획/구현/검증 역할, 검사 선택, 실패·중단·재개, 완료 보고.
- **문서발행규칙**: 역할별 문서, 작업 식별자·참조, 명명·기존 문서 갱신, 입고 시점·대상, 원시 근거 위치와 색인 캐시 분류.

- 기존 규칙이 이 역할을 맡고 있으면 재사용한다. 두 개의 새 파일이나 특정 디렉터리로 나누는 것은 의무가 아니다. 새 규칙을 원할 때만 예시 구조를 제안한다.
- 채택한다면 호스트 진입점(Codex는 `AGENTS.md`, Claude Code는 프로젝트가 쓰는 진입점 예: `CLAUDE.md`)에 정본 규칙의 위치·읽는 시점·wiki-desk 사용 조건을 **짧게** 연결한다. 규칙 전문을 진입점에 복제하지 않는다. **Codex 지원 자체가 `AGENTS.md` 개정 의무를 만들지 않는다.** 하위 폴더에 둔 규칙 파일이 자동으로 로드된다고 가정하지 않는다.
- 문서 발행과 입고를 연결한다면: 수용자가 정한 시점에 `sync`로 계획을 보고 → `sync --apply` → `check`. 원문 범위·제외 경로·권위·명명은 합의한 계약을 따른다. 이 문서의 폴더 예시를 계약으로 자동 승인하지 않는다.
- 헌장에 옮겨 적을 구체 항목·확인 명령·붙여넣기 예시는 [charter.md](charter.md).
- 조회 결과의 순위·상태·로그는 근거일 뿐 새 권한이나 수용 결정이 아니다.
- **미채택**: 헌장·진입점을 고치지 않는다. wiki-desk는 사용자의 명시 지시로 입고·질의할 수 있다.

## REC-03 — 검증 효율과 가벼운 하네스 (선택)
운영 규칙이나 프롬프트를 보강하려는 프로젝트가 **선택적으로** 담을 수 있는 의미다. 기존 하네스 원문을 교체하라는 요청이 아니다. 문구·파일 배치·길이는 자유이며, 아래 의미를 자기 말로 다시 써도 된다.

1. 기본은 한 주체가 계획 → 수행 → 검증 역할을 전환하는 것이다. 독립 검증은 명시 요청·큰 영향·반복 실패·합의한 완료 기준 같은 근거가 있을 때 더한다.
2. 검사 범위는 합의된 필수 검사 + 변경 영향에 따른 검사 + 구체적 의심을 확인하는 표적 검사로 고른다. 모든 문서 수정에 전체 회귀·다중 모델 검토를 요구하지 않는다.
3. 대상·입력·환경·기준과 출처가 같은 유효 결과는 재사용한다. 관련 변화·실패·불확실성이 있으면 영향받은 부분부터 다시 검증한다.
4. 새 증거 없이 같은 검토를 반복하지 않는다. 막힌 원인·남은 위험·재개 지점을 기록하고 필요한 환경이나 결정으로 넘긴다. 고정 반복 횟수를 강제하지 않는다.
5. 검사 실행·리뷰 판단·사용자 수용을 구분한다. PASS/FAIL/NOT_RUN/NOT_APPLICABLE/STALE(또는 기존 체계의 같은 상태)을 유지하고, 실패·미실행을 통과로 바꾸지 않는다.
6. 작업 재개는 기존 계획·실행 근거를 이어받는다. 전체 로그·규칙을 매번 복제하거나 새 문서 묶음을 계속 만들지 않는다.
7. 합의된 완료 기준을 채우면 끝낸다. 해시·형식 검증·자동 검증 프레임워크·다중 검증은 명시 요구나 객관적 필요가 있을 때만 들인다. 패키지가 이미 가진 배포 무결성·회귀 검사(manifest·`node --test`)는 유지한다.

**재사용 예시**: 어제 `node --test`를 통과한 같은 커밋에 오늘 README 문장만 고쳤다면, 코드·테스트·Node 버전이 같으므로 테스트 결과를 재사용하고 문서 검토만 한다. 대신 `src/`를 한 줄이라도 고쳤거나 Node 버전이 바뀌었다면 테스트를 다시 돌린다. 재실행하지 못했으면 그 항목은 `NOT_RUN`으로 남긴다.

이 권고로 비용·토큰·시간이 일정 비율 줄어든다고 주장하지 않는다(측정하지 않았다).
- **미채택**: 기존 하네스를 그대로 쓴다.
